# LearnedFTL 논문·레포 분석 및 보드 이식 설계

- 논문: Wang et al., "LearnedFTL: A Learning-based Page-level FTL for Reducing Double Reads in Flash-based SSDs", HPCA'24
- 레포: https://github.com/astlxmu/LearnedFTL (커밋 `4702166`, 2024-09-09 "Fix bugs.")
- 구현 위치: `cosm-plus-sys.sdk/run-lftl`, 기록용 사본 `NewSSS/firmware/learnedftl`

**분석 범위:** 논문은 14쪽 전부 읽었습니다. 레포는 7만 개 넘는 파일 대부분이 QEMU 본체이므로, LearnedFTL 구현인 `hw/femu/bbssd/ld-tpftl.c/.h`(약 3,300줄), `util.c`, `bb.c`, `meson.build`, README를 전부 읽었습니다. `tpftl.c`, `dftl.c`, `leaftl.c`, `ftl.c`는 함수 목록과 설정값만 확인했습니다. 레포의 FEMU를 실행해 보지는 않았고, 아래 내용은 코드를 읽어 판단한 것입니다.

## 1. 논문 요약

**해결하려는 문제.** DFTL 계열은 매핑 캐시(CMT)에 없는 LPN을 읽을 때 translation page를 한 번 더 읽어야 합니다(double read). 지역성이 없는 랜덤 읽기에서는 CMT를 전체 매핑의 50%까지 늘려도 hit ratio가 25.9%에 그칩니다(Fig. 3). LeaFTL은 모델까지 캐시에 올리고 예측도 틀릴 수 있어 triple read까지 발생합니다(랜덤 읽기의 43%, Fig. 6b).

**핵심 아이디어.** TPFTL을 그대로 두고, GTD 항목마다 작은 학습 모델을 항상 메모리에 둡니다. 비트맵이 "이 LPN은 예측이 정확하다"고 보장하는 경우에만 예측을 씁니다. 그래서 잘못된 예측에 따른 추가 비용이 없습니다.

```
읽기: CMT hit → 끝
      CMT miss, 비트맵 1 → 모델로 PPN 계산, 데이터 1회 읽기
      CMT miss, 비트맵 0 → translation page 읽기 + 데이터 읽기 (기존 double read)
```

| 기법 | 내용 |
|---|---|
| In-place-update 선형 모델 (III-B) | `<k, b, off>[N]` + LPN당 1비트 비트맵. 크기가 고정되어 LeaFTL의 compaction이 필요 없음. 논문 기준 모델당 128B, 8 piece |
| Virtual PPN (III-C) | 주소 자릿수 순서를 channel→lun→plane→page→block으로 바꿔, 병렬 쓰기로 흩어진 PPN을 연속된 번호로 표현 |
| 그룹 기반 할당 (III-D) | 인접 GTD 항목 64개를 한 그룹으로 묶고, 그룹이 플래시 블록을 통째로 소유. 뜨거운 그룹은 차가운 그룹의 빈 페이지를 빌림(cross-group) |
| 모델 학습 (III-E) | 순차 초기화(순차 쓰기를 y=x 모델로 바로 반영) + GC 학습(유효 매핑 정렬 → 재기록 → 학습 → 평가) |

**논문 실험 결과 (FEMU, 32GB, 64 parallel unit, 4KB, psync 64 스레드).** 랜덤 읽기 처리량은 DFTL, TPFTL, LeaFTL 대비 각각 1.5, 1.4, 1.6배이고, double read를 최대 55.5% 줄였습니다. P99 지연은 평균 5.5배(TPFTL), 8.2배(LeaFTL) 개선됐습니다. 정렬과 학습은 그룹 항목당 약 50µs로 GC 시간의 최대 3.2%입니다.

## 2. 레포 구조

- FEMU(QEMU 기반 SSD 에뮬레이터)의 blackbox 모드 위에 구현했습니다. `meson.build`에서 `bbssd/*.c` 중 하나를 골라 FTL을 바꿉니다.
- LearnedFTL은 `ld-tpftl.c`입니다. 주요 함수는 `ssd_read`, `ssd_write`, `model_predict`(예측), `model_training`(학습), `batch_line_do_gc`(그룹 GC), `should_do_gc_v3`(GC 트리거)입니다.
- 설정값: 4KB 페이지, 8채널×8LUN, 라인 256개(32GB), 라인당 32768페이지, TP당 512엔트리, 그룹당 TP 64개, 모델당 8 piece, `gc_threshold=5`.

### 논문과 코드가 다른 부분

이식할 때 가장 중요한 내용입니다. 레포 코드를 그대로 옮기면 보드에서 동작하지 않거나 데이터가 깨집니다.

| 항목 | 논문 설명 | 레포 코드 (`ld-tpftl.c`) | 이식에 미치는 영향 |
|---|---|---|---|
| 예측 정확성 | 비트맵 1이면 항상 정확 | `model_predict`가 전체 매핑표 `maptbl`과 비교해 틀리면 double read로 처리 (L2500-2506) | **보드에 그런 오라클은 없음.** 비트맵 자체가 정확해야 함 |
| 쓰기 시 비트 해제 | 비트를 0으로 변경 | 해당 코드가 주석 처리됨 (L2671-2673) | 오라클이 가려 주는 버그. 그대로 옮기면 옛 데이터를 읽게 됨 |
| 순차 초기화 | 모델을 제자리 갱신 | `lr_node lrn`을 **값으로 복사**한 뒤 수정해 원본이 안 바뀜 (L2726). 비트맵만 1로 설정 (L2748) | 실제로는 동작하지 않음. 직접 구현 필요 |
| Cross-group 할당 | 핵심 기법으로 설명 | `borrow_or_gc` 전체가 주석 처리된 TODO (L411-440, L653) | **구현이 없음.** 대안 필요 (3.2절) |
| GC 대상 선정 | 무효 페이지가 가장 많은 그룹 | `victim_list`에서 라인이 2개 이상인 첫 그룹 (L485-506) | 논문대로 직접 구현 |
| TP 쓰기 비용 | 쓰기 증폭 절감의 근거로 제시 | TP 쓰기, TP GC 쓰기, TP 지우기의 지연이 모두 주석 처리됨 (L1348-1352, L1991-1997, L2072-2078). GC 후 TP 갱신도 주석 (L2267-2272) | 레포 수치만으로는 비용을 판단할 수 없음. 보드에서는 실제 비용 발생 |
| CMT 크기 | 전체 매핑의 1.5% | 8192엔트리 고정, 약 0.1% (L809) | 실험 조건 비교 시 주의 |
| 모델 크기 | k, b 각 2B **float16**, off 2B 정수, 비트맵 512bit, 총 128B | `float`(32비트) 2개 + `int` 2개 × 8, 비트맵은 LPN당 **1바이트** (L964) | 메모리 수치가 논문과 다름 |
| 쓰기 포인터 | 전체 그룹 | 240개만 초기화, 전체는 256개 (L358) | 그룹 240 이상 접근 시 NULL 역참조 |
| 부동소수점 | k, b를 float16으로 저장. 반올림과 비트맵 덕분에 정밀도 요구가 낮아 Float8도 고려할 수 있다고 언급 (Model's Space Overhead) | 학습(`util.c` `LeastSquareNew`)과 예측(`predict`)에 32비트 `float` 사용. 주석에 정밀도 문제 언급 (L2499) | 보드에서는 k를 Q0.15 정수(2B), base를 32비트 정수로 대체. 실수 연산 없음 |
| 스택 사용 | - | GC에서 약 768KB VLA (L2243, L2380) | 보드 스택은 8KB. 그대로 불가 |

통계에도 주의할 점이 있습니다. `model_hit_num`이 검증 전에 증가하므로(L2582) 레포의 모델 hit 수치에는 틀린 예측이 섞일 수 있습니다.

## 3. 보드 이식 설계

### 3.1 보드 구조와의 대응

| 논문/레포 | 보드 (Micron 8C2W) | 비고 |
|---|---|---|
| 페이지 4KB, TP당 512엔트리 | 16KB, TP당 4096엔트리 | |
| 라인 = 블록 64개, 32768페이지 | 라인 = 가상 블록 16개, 4096페이지 | 전체 2048라인 |
| 그룹 = TP 64개 | **그룹 = TP 1개** | TP 1개가 라인 1개 분량을 담음 |
| VPPN 변환 필요 | **기존 VSA가 곧 VPPN** | `VSA = die + 16×(block×256 + page) = line×4096 + offset` |
| piece당 64 LPN | 동일하게 64 LPN | 그룹당 최대 64 piece |
| 불량 블록 | 펌웨어의 기존 리매핑 사용 | 가상 블록이 불량인 라인은 통째로 제외 |

### 3.2 논문과 다르게 구현한 부분과 이유

**(1) 그룹 범위를 라인 용량보다 작게 설정 (4096 → 3776 LPN).** 시뮬레이터로 발견한 문제입니다. 그룹 범위가 라인 용량과 같으면, 모든 LPN이 유효한 상태에서는 GC 직후 새 라인이 이미 가득 찹니다. 전체 용량 랜덤 쓰기에서 **WA가 3921**까지 올랐습니다. 논문의 해법인 cross-group은 레포에 없고, 모든 그룹이 가득 찬 상태에서는 빌릴 빈 페이지도 없습니다. 그래서 라인마다 여유 공간을 남겼습니다. 이는 **논문에 없는 변경**이며, 발표 시 명시해야 합니다.

**(2) Cross-group 할당은 구현하지 않았습니다.** (1)로 대체했고 향후 과제입니다. 그 결과 전체 용량 랜덤 쓰기의 WA(약 12.8)가 논문 Fig. 14c의 범위(그래프 판독 약 5~8)보다 높습니다.

**(3) 정수 연산.** k는 Q0.15 고정소수점이고, 학습과 예측이 같은 정수 코드를 씁니다. 학습 때 정확했던 비트가 반올림 차이로 틀어질 수 없습니다.

**(4) piece 범위 고정.** `off`를 저장하지 않아 조회가 O(1)입니다. LPN 구멍이 있으면 범위가 고정된 piece의 적합도가 떨어지므로, 최소제곱 결과와 "가장 긴 연속 구간에 y=x+b" 중 더 많이 맞히는 쪽을 고릅니다.

**(5) 예측 이중 보호.** 비트맵이 맞으면 틀릴 일이 없지만, DRAM의 역매핑(P2L)으로 한 번 더 확인합니다. 불일치하면 TP로 처리하고 `modelRejected`를 올립니다. 정상이면 항상 0이어야 합니다.

**(6) 번역 페이지 대기 방식.** 기존 `run-dftl`처럼 `SyncAllLowLevelReqDone()`으로 SSD 전체 큐를 비우지 않고, 해당 요청 하나만 기다립니다.

**(7) 정렬 불필요.** TP가 LPN 순서의 배열이므로 GC 때 정렬 없이 순서대로 읽으면 됩니다.

### 3.3 코드 구조

| 파일 | 역할 |
|---|---|
| `lftl_config.h` | 실험 변수: `LFTL_ENABLE_MODEL`, `LFTL_CMT_CAPACITY`, `LFTL_GROUP_SPAN`, `LFTL_SHADOW_CHECK` |
| `lftl_model.c/h` | 모델, 비트맵, 순차 초기화, 학습 |
| `lftl_cmt.c/h` | TPFTL 2단계 LRU 캐시 |
| `lftl_core.c/h` | 읽기/쓰기 변환, 그룹 할당, 그룹 GC, TP 관리, 통계 |
| `lftl_port.h`, `lftl_port_cosmos.c` | 보드 의존부 (요청 풀, NAND I/O) |

GreedyFTL에서 수정한 기존 파일은 4개, 약 20줄입니다: `address_translation.c`, `memory_map.h`, `request_transform.c`, `nvme/nvme_main.c`.

### 3.4 메모리

| 항목 | 크기 |
|---|---|
| 모델 1개 (base 256B + k 128B + 비트맵 512B) | 896B |
| 전체 모델 (1999그룹) | 약 1.7MB |
| 전체 메타데이터 (`LFTL_META`, CMT 8192 기준) | 2152KB |
| 참고: GreedyFTL 전체 매핑표 | 32MB |

**주의할 점이 두 가지 있습니다.**
- 역매핑(P2L) 32MB는 GreedyFTL처럼 DRAM에 남아 있어, 실제 DRAM 사용량이 줄어든 것은 아닙니다. 위 수치는 정방향 매핑 구조만의 크기입니다.
- 모델 메모리(1.7MB)가 CMT(엔트리당 24B × 8192 = 약 196KB)보다 훨씬 큽니다. 공정하게 비교하려면 DFTL/TPFTL의 CMT를 **같은 총 메모리**(약 96,000엔트리)까지 늘린 결과도 함께 측정해야 합니다.

## 4. 검증 결과

**실제 보드에서는 아직 실행하지 않았습니다.** 아래는 실제 `lftl_core/model/cmt` 코드를 PC에서 시뮬레이션 NAND 위에 돌린 결과입니다. 타이밍, 병렬성, 데이터 버퍼를 모델링하지 않으므로 **처리량이나 지연은 알 수 없고**, 매 접근마다 다음을 확인합니다.

- 읽은 데이터가 해당 LPN의 최신 버전인지
- 페이지를 순서대로 프로그램하는지
- 지우기에 넘기는 페이지 수가 실제와 같은지 (틀리면 보드에서 무한 대기)
- 모든 변환이 전체 shadow 맵과 일치하는지

**결과:** 2048라인 규모(시드 1)와 축소 규모(시드 1, 2, 3)에서 위반 0건, `modelRejected` 0건입니다. ARM 툴체인 빌드도 기본, shadow 켬, 모델 끔 세 구성 모두 성공했습니다.

시뮬레이터가 잡아낸 문제는 두 가지입니다. GC 시 shadow 맵 미갱신(보드 bring-up에서 멀쩡한 동작을 오류로 멈췄을 문제)과 WA 3921 문제입니다.

### 읽기 경로 비율 (2048라인, 범위 3776, CMT 8192)

| 단계 | 모델 끔 (TPFTL, 범위 3840): double read | 모델 켬: 모델 hit | 모델 켬: double read |
|---|---|---|---|
| **전체 용량 시나리오, 16KB 랜덤 읽기** | | | |
| 순차 채우기 직후 | 99.9% | 99.9% | 0.0% |
| 랜덤 쓰기 1회 후 | 99.9% | 94.6% | 5.3% |
| 랜덤 쓰기 6회 후 | 99.9% | 95.7% | 4.2% |
| **기존 FIO 조건 (2GB 범위, 128KB)** | | | |
| 순차 쓰기 후 순차 읽기 | 12.5% | 93.8% | 0.0% |
| 랜덤 쓰기 1회 후 랜덤 읽기 | 11.7% | 37.4% | 7.1% |
| 랜덤 쓰기 7회 후 랜덤 읽기 | 11.7% | 14.6% | 9.9% |

**해석에 주의할 점**
- 모델 hit 95%는 논문의 55.5%보다 훨씬 높은데, 우수하다고 단정하면 안 됩니다. 시뮬레이션은 합성 부하이고 데이터 버퍼의 재배열이 없으며, 모든 LPN이 채워진 상태라 모델에 유리합니다. 실제 수치는 보드에서 확인해야 합니다.
- **기존 조건(128KB, 2GB)에서 랜덤 쓰기 후에는 효과가 작습니다.** 128KB 요청은 TP 한 번으로 8개 매핑을 가져오는 데다, GC가 드물어 모델이 금세 낡습니다. LearnedFTL의 효과를 보려면 **작은 블록 크기와 넓은 범위**로 측정해야 합니다.

### 그룹 범위별 쓰기 증폭 (2048라인)

| 범위 | 그룹 수 | 여유 라인 | 랜덤 쓰기 WA | 순차 재쓰기 WA |
|---|---|---|---|---|
| 4096 | - | - | 3921 (128라인 규모, 1회차) | - |
| 3840 | 1966 | 79 | 15.6 | 1.92 |
| **3776 (기본값)** | 2000 | 45 | 12.8 | 1.96 |
| 3712 | 2034 | 11 | 10.8 | 4.53 |

그룹 수는 시뮬레이터 기준입니다. 보드에서는 용량 계산식에 따라 3776일 때 1999그룹입니다.

## 5. 알려진 한계

1. **보드 미검증:** 요청 의존성 처리, 번역 페이지 대기, 실제 처리량은 보드에서만 확인할 수 있습니다.
2. **GC가 전경에서 동작:** 그룹 GC는 최대 3776페이지를 복사하므로, 그동안 새 NVMe 명령 처리가 밀립니다. 꼬리 지연에 영향이 있을 것으로 보이며, 크기는 측정이 필요합니다.
3. **전원 차단 복구 없음:** GreedyFTL과 같습니다. 재부팅하면 내용이 초기화됩니다.
4. **WA:** 전체 용량 랜덤 쓰기에서 논문 수치보다 높습니다.
5. **`-O0` 빌드:** 비교 가능성을 위해 기존과 같은 플래그를 씁니다.
6. **Rewrite 기반 학습(III-E3)은 미구현:** 논문도 FEMU에서 구현하지 않았습니다.

## 6. 기존 `run-dftl`에서 발견한 점

코드를 읽고 확인한 내용이며, 실행해서 검증하지는 않았습니다. GreedyFTL 대비 7~30배 느린 결과의 원인 후보입니다.

- **캐시 miss마다 `SyncAllLowLevelReqDone()`:** SSD의 모든 진행 중인 요청이 끝날 때까지 기다립니다 (`dftl_gtd.c`의 `ReadTransPage`/`WriteTransPage`).
- **배치 쓰기 없음:** 더티 엔트리를 하나 내보낼 때마다 TP 읽기+쓰기가 발생합니다 (`DftlGtdWritebackMapping`).
- **무효화 순서:** `InvalidateOldVsa`가 CMT의 옛 매핑을 지우지 않은 채 할당으로 넘어갑니다. 그 사이 GC가 돌면 무효 페이지를 유효로 판단해 복사할 수 있습니다.

따라서 `run-lftl`과 현재 `run-dftl`을 바로 비교하면 학습 모델의 효과와 위 차이가 섞입니다. **모델 효과만 보려면 `run-lftl`의 `LFTL_ENABLE_MODEL=0`(TPFTL)과 비교**해야 합니다.
