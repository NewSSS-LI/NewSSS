# Cosmos+ OpenSSD — DFTL FIO Benchmark Results (v1)

**테스트 날짜**: 2026-09-30
**FTL**: DFTL (CMT 4096 entries, GTD, translation block pool 다이당 4개) — `run-dftl`
**대상**: `/dev/nvme0n1` (raw device, 파일시스템/파티션 없음)
**파라미터**: bs=128k, iodepth=4, size=128M — 교수님 피드백 반영("너무 클 필요 없다"), size=128MB는 bs=128k에 맞춰 자체적으로 정한 값 (교수님이 정확히 언급한 값은 기록 유실, 추후 확인 필요)

## 실행 명령어

```bash
sudo fio --name=seqwrite --filename=/dev/nvme0n1 --rw=write --bs=128k --size=128M --numjobs=1 --iodepth=4 --ioengine=libaio --direct=1 --group_reporting
sudo fio --name=seqread --filename=/dev/nvme0n1 --rw=read --bs=128k --size=128M --numjobs=1 --iodepth=4 --ioengine=libaio --direct=1 --group_reporting
sudo fio --name=randwrite --filename=/dev/nvme0n1 --rw=randwrite --bs=128k --size=128M --numjobs=1 --iodepth=4 --ioengine=libaio --direct=1 --group_reporting
sudo fio --name=randread --filename=/dev/nvme0n1 --rw=randread --bs=128k --size=128M --numjobs=1 --iodepth=4 --ioengine=libaio --direct=1 --group_reporting
```

## 결과

| 테스트 | IOPS | 대역폭 | 평균 지연시간 | 비고 |
|---|---|---|---|---|
| Sequential Write | 81 | 10.2 MiB/s (10.7 MB/s) | 48.8 ms | 지연시간 이봉 분포 (42ms대 다수 + 105ms대 꼬리, 아래 분석 참고) |
| Sequential Read (1회차) | 258 | 32.3 MiB/s (33.8 MB/s) | 15.5 ms | 콜드 |
| Sequential Read (2회차) | 611 | 76.5 MiB/s (80.2 MB/s) | 6.5 ms | 1회차 직후 바로 실행 |
| Random Write | 112 | 14.1 MiB/s (14.8 MB/s) | 35.5 ms | |
| Random Read (1회차) | 258 | 32.3 MiB/s (33.9 MB/s) | 15.4 ms | 콜드 |
| Random Read (2회차) | 619 | 77.4 MiB/s (81.2 MB/s) | 6.4 ms | |
| Random Read (3회차) | 619 | 77.4 MiB/s (81.2 MB/s) | 6.4 ms | 2회차와 거의 동일 — 수렴/plateau |
| Sequential Read (3회차) | 488 | 61.1 MiB/s (64.0 MB/s) | 8.1 ms | randwrite+randread 2회가 사이에 끼어든 뒤 실행 — 2회차보다 느려짐 |

## 분석

**Sequential Write 지연시간 이봉 분포**: 128MB ÷ 128KB(요청 크기) = 슬라이스(16KB) 기준 8,192개를 건드리는데, CMT 용량은 4,096개라 테스트 절반 지점부터 계속 eviction이 발생. dirty 항목이 쫓겨날 때마다 translation page read-modify-write(NAND I/O 2회 추가)가 붙어서, clat percentile 90~99.5th구간이 42ms대에서 105ms대로 튐. DFTL의 demand-paging 오버헤드가 실측으로 확인된 첫 사례.

**Random Read: 1→2회차 급상승 후 2→3회차 거의 동일(수렴/plateau)** — 가장 깔끔한 증거. 1회차(콜드, 32.3MiB/s) → 2회차(웜업, 77.4MiB/s) → 3회차(77.4MiB/s, 2회차와 IOPS·지연시간까지 거의 동일). CMT 용량(4096)이 작업 범위(8192 슬라이스)의 절반이라, 반복해도 딱 거기까지만 좋아지고 그 이상은 개선되지 않음 — "메모리 예산이 성능 상한을 결정한다"는 걸 정량적으로 보여주는 데이터.

**Sequential Read: 2회차(76.5MiB/s)보다 3회차(61.1MiB/s)가 더 느림** — 얼핏 이상해 보이지만, 2회차는 1회차 직후 바로 실행된 반면 **3회차는 그 사이에 randwrite 1회 + randread 2회가 CMT를 어지럽혀놓은 뒤 실행됨.** 즉 순차 접근으로 데워진 CMT 항목 일부가 그 사이 랜덤 접근에 밀려나서(eviction), 3회차 때는 2회차만큼 따뜻하지 않았던 것. **서로 다른 워크로드가 번갈아 들어오면 캐시 워밍업 효과가 깨지는(cache pollution/interference) 현상**을 보여줌 — GreedyFTL에서는 절대 나타날 수 없는, 순수하게 DFTL의 캐시 기반 구조 때문에 생기는 현상.

**Random Write(14.1MiB/s)가 Sequential Write(10.2MiB/s)보다 빠르게 나온 점**: 일반적인 SSD 특성과 반대인데, 각 테스트가 9~12초로 짧고 iodepth=4로 낮아 표본이 작아서 생긴 변동(variance)일 가능성이 높음. 반복 측정으로 확인 필요.

## 중요 — 이후 GreedyFTL 재측정에서 발견된 사고 (2026-09-30 밤)

이 DFTL 결과를 측정한 후, 같은 날 밤 GreedyFTL을 동일 조건(및 이후 bs=1M/iodepth=64/size=1G 등 여러 파라미터)으로 재측정했는데 **GB/s대의 물리적으로 불가능한 수치**가 반복적으로 나왔음 (Sequential Write 5000~7000MB/s, Random Write IOPS 296,000 등). 오랜 디버깅 끝에 원인 확인: **호스트 PC(SSSLab-Com4)를 여러 번 재부팅/rescan하는 사이에 Cosmos+ OpenSSD 보드가 PCIe에서 인식이 끊겼는데(`lspci`에 Xilinx Device 7028 자체가 안 뜸), `/dev/nvme0n1`이라는 장치명이 호스트 PC 자체의 내장 NVMe SSD로 넘어가 있었음.** 즉 그 GreedyFTL 재측정은 전부 우리 보드가 아니라 호스트 내장 SSD를 측정한 것 — 전부 무효.

**이 DFTL 결과(위 표)는 GreedyFTL 이상 현상을 발견하기 전, 즉 보드가 정상 인식되던 시점에 측정한 것으로 추정됨** (숫자가 물리적으로 타당한 범위 — 수십 MB/s대 — 였고, CMT eviction으로 설명되는 지연시간 패턴이 명확했던 것 자체가 실제 보드를 측정했다는 방증). 다만 **100% 확신은 못 하므로, 다음 세션에서 GreedyFTL을 다시 측정하기 전에 반드시 `lspci | grep -i non-volatile`로 Xilinx Device 7028이 뜨는지부터 확인한 뒤, 이 DFTL 결과도 시간 여유 되면 재검증할 것.**

**교훈**: fio 돌리기 전에 매번 `lspci`로 보드 인식부터 확인하는 습관 필요. 특히 호스트 PC를 재부팅/rescan한 직후에는 필수.

## 재검증 완료 (v2, 2026-09-30 밤, 보드 인식 확인 후 재측정)

`lspci`로 Xilinx Device 7028 인식 재확인한 뒤 동일 커맨드로 재측정. **위 v1 결과와 대부분 2~10% 오차 내로 재현됨** — v1이 실제로 우리 보드를 측정한 게 맞았다는 게 사실상 확정됨.

| 테스트 | v1 | v2(재검증) |
|---|---|---|
| Sequential Write | 10.2 MiB/s (IOPS 81) | 25.7 MiB/s (IOPS 205) — variance 큰 편 |
| Sequential Read 1회차(콜드) | 32.3 MiB/s | 35.5 MiB/s |
| Sequential Read 2회차 | 76.5 MiB/s | 78.9 MiB/s |
| Sequential Read 3회차 | 61.1 MiB/s (중간에 random 테스트 끼어들어 간섭) | **78.7 MiB/s (방해 없이 연속 실행, plateau 유지)** |
| Random Write | 14.1 MiB/s (IOPS 112) | 14.6 MiB/s (IOPS 117) |
| Random Read 1회차(콜드) | 32.3 MiB/s | 33.0 MiB/s |
| Random Read 2회차 | 77.4 MiB/s | 77.6 MiB/s |
| Random Read 3회차 | 77.4 MiB/s | 77.6 MiB/s |

**v2에서 확인된 중요한 점**: 이번엔 seqread 3회가 랜덤 테스트 간섭 없이 연달아 실행되어, **Sequential Read도 Random Read와 동일하게 콜드→웜업→plateau 패턴(35.5→78.9→78.7)을 깨끗하게 보여줌.** v1에서 3회차가 느려졌던 건 정말로 중간에 낀 randwrite/randread의 캐시 오염 때문이었다는 게 이번 재현으로 뒷받침됨 — cache pollution 가설이 한 번 더 검증됨.
